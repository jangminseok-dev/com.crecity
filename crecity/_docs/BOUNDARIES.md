## 1. 트랜잭션 경계 원칙 (필수)

이 프로젝트는 **단일 프로세스 + 단일 PostgreSQL의 모듈러 모놀리스**다.
Saga·분산 트랜잭션·보상 트랜잭션은 도입하지 않는다. 대신 경계를 다음 원칙으로 긋는다:

1. **원자성이 필수인 상태 변경은 같은 스포크(=같은 DB 트랜잭션)에 둔다.**
   교차 스포크 보상 로직이 필요해 보인다면 그건 이벤트 문제가 아니라 경계를 잘못 그은 것이다.
2. **결과적 정합성으로 충분한 부수효과**(알림 발송, 통계, 랭킹 반영)만 허브 이벤트로 뺀다.
   유실이 허용되지 않는 부수효과는 **Outbox 패턴**(커밋과 같은 트랜잭션에 이벤트 행 기록 →
   워커가 발행)으로 처리한다. Outbox는 **첫 소비자(알림 발송)가 생길 때 도입**한다 — 지금은 없다.
3. **외부 API(PG 승인·은행 이체·알림톡)는 원자적일 수 없다.** 상태 기록 + 재시도로 다루며,
   이런 외부 접점은 전용 스포크(payment·notification)로 격리한다.

## 2. 스포크 경계

### 현재 구축됨

| 앱 | 책임 | 소유 데이터 |
|---|---|---|
| hub | 교차 협력 계약(포트·DTO) 소유, 추후 Outbox 이벤트 중계 | (없음 — 계약만) |
| auth | 계정·인증·크리에이터/브랜드 계정 배타성(동일 이메일 겸용 불가), 추후 RBAC | 사용자, 리프레시 토큰 |
| creator | 크리에이터 프로필·심사 상태·판매 패키지·고유 슬러그(SEO 단위) | 프로필, 패키지, 포트폴리오 |
| order | 주문 상태머신(§4) · **에스크로/잔액 원장**(돈의 장부 — §3). 2026-08-10 1차 구축, 장바구니·취소·크레딧 사용은 예정 | 주문, 원장(예치·잔액·크레딧) |
| payment | 외부 결제 접점(§3): 토스페이먼츠 pay-in(승인·취소 보정) 2026-08-10 구축 — 인출·3.3% 원천징수·지급명세서는 예정 | PG 승인 기록(payment_intents) |
| review | 3축 평점(소통/기한/만족)·리뷰 블러 정책 — 2026-08-10 구축(신고·중재는 예정) | 리뷰 |

### 후속 (착수 순서대로)

| 앱 | 책임 | 소유 데이터 | 비고 |
|---|---|---|---|
| campaign | 역경매 공고·크리에이터 지원 | 공고, 지원서 | |

| notification | 알림톡·이메일 발송 (Outbox 첫 소비자) | 발송 시도 기록 | Outbox와 함께 도입 |

  브랜드 전용 데이터가 실제로 생기면 그때 분리를 검토한다.

## 3. 돈의 경계 — order와 payment 분리 기준

리뷰에서 지적된 "주문↔결제 교차 트랜잭션" 문제는 경계로 해소한다:

- **원장(ledger)은 order 소유.** 다음 전이는 전부 order 내부의 단일 DB 트랜잭션이다:
  - 크리에이터 수락 → 에스크로 예치 확정
  - 거절/72h 만료 → 브랜드 잔액(크레딧) 환불
  - 브랜드 승인(또는 72h 자동 승인) → 주문 완료 + 크리에이터 잔액 적립
- **payment는 돈이 시스템 밖과 만나는 지점만 담당.** PG 카드 승인(pay-in), 은행/PayPal 이체(pay-out),
  세무 서류. 외부 API라 어차피 원자성이 불가능한 것들만 모였으므로 상태 기록+재시도 도메인이다.
- **경계를 넘는 두 흐름** (둘 다 외부 API가 끼므로 2단계가 본질이다 — Saga가 아니라 정상 설계):
  - 결제: payment가 PG 승인 기록 → 성공 시 order가 주문 생성+예치(원자적).
    승인 후 주문 생성 실패 시 PG 취소(재시도 가능한 단일 보정 — payment 내부 책임).
  - 인출: order가 잔액 차감+인출 예약을 원자적으로 기록 → payment가 이체 실행 →
    결과에 따라 order가 확정 또는 복원. 이체 결과가 불명이면 재조회로 수렴(즉시 복원 금지).

## 4. 주문 상태머신 (collabstr-analysis §3.8 — order 앱의 도메인 핵심)

```
PENDING_ACCEPT ──수락──▶ IN_PROGRESS ──제출──▶ IN_REVIEW ──승인/72h경과──▶ COMPLETED
      │                                     │
      ├─ 거절 ─▶ REFUNDED                    └─ 수정 요청 ─▶ IN_PROGRESS (반복, 무제한)
      └─ 72h 만료 ─▶ REFUNDED (+랭킹 페널티)
취소: 양측 합의제 — 합의 전까지 에스크로 유지, CANCELLED 시 브랜드 크레딧 환불
```

- 상태 전이는 **순수 파이썬으로 `order/domain`에 구현**한다(도메인 순수성 계약 활용) —
  스텁 없이 단위 테스트 가능해야 한다.
- **72h 타이머**: 이벤트 예약이 아니라 **마감시각 저장 + 주기 스캔**으로 처리한다.
  주문 행에 `deadline_at`을 저장하고, cron 스크립트(레퍼런스 cron 패턴)가 주기적으로
  만료 주문을 조회해 전이시킨다. 크래시에 안전하고 단순하다. 정밀도는 분 단위면 충분.

## 5. 허브 계약 (초기 후보)

스포크 간 협력이 실제로 필요해지는 시점에 하나씩 추가한다 — 선제 정의 금지.

| 계약(포트) | 소비자 → 제공자(게이트웨이 구현) | 필요 시점 |
|---|---|---|
| 크리에이터 요약 조회 | order/campaign → creator | 주문 생성 검증 시 |
| 회원 디렉토리 조회 | admin → auth | 어드민 심사 화면 (레퍼런스 동일 패턴) |
| 주문 이벤트 발행(Outbox) | order → notification 소비 | 알림 발송 구현 시 |
| 잔액 조회 | payment → order | 인출 구현 시 |

## 6. 적용하지 않기로 확정한 것 (외부 리뷰 대응)

- **인메모리 이벤트 버스·Saga 패턴**: 단일 DB 모놀리스에 불필요. §1 원칙으로 대체.
- **CQRS 우회 예외(어댑터→리포지토리 직접 접근)**: 기각. 수직 슬라이스 1:1 컨벤션은
  에이전트 하네스의 핵심 장치이며, 우회로는 규율 붕괴의 시작점이다.
  보일러플레이트 부담은 슬라이스 생성 스크립트로 흡수한다.
  읽기 모델 분리(CQRS)는 목록·검색 성능 문제가 실측되면 정식 슬라이스로 도입한다.
- **클라우드 CI 복원**: 기각(사용자 확정 정책). 대신 로컬 git 훅이 안전망이다 —
  pre-commit=`lint-imports`, pre-push=`pytest` (`scripts/git-hooks/`, `core.hooksPath`).

## 7. 확정 사항 (2026-08-10 사용자 승인)

1. **원장은 order 소유** — §3 경계 그대로. ledger 별도 스포크 대안은 기각
   (승인↔적립 원자성 붕괴). 재제안 금지.
2. **착수 순서: creator → auth(소셜 로그인) → order → payment.**
   근거: 데이터 의존(주문은 패키지가 전제), SEO 자산(공개 프로필 SSR) 조기 확보, 외부 의존 0.
3. **PG는 토스페이먼츠 우선** — 지급대행(셀러 정산)·에스크로 공식 제공 확인(2026-08-10).
   payment는 헥사고날 포트 뒤에 격리해 교체 가능하게 설계(포트원 등 멀티 PG 추상화는 중복이라 기각).
   계약 전 실사 항목(사업 확인, 런칭 전): 에스크로+지급대행 동시 계약 조건, 정산 주기,
   원천징수 3.3% 처리 주체(플랫폼 자체 처리 전제 — payment 앱 몫).
4. **수수료율: 설정값 + 주문 시점 스냅샷 구조** — 요율 하드코딩 금지, 주문 생성 시점의
   요율을 원장에 스냅샷 기록(요율 변경의 소급 차단). 초기값 **브랜드 10% / 크리에이터 10%**
   (Collabstr 10%+15% 대비 크리에이터 측 인하 — 원천징수 3.3% 체감 부담·공급 확보 우선).
   숫자는 런칭 전 경쟁사 요율 실사 후 재조정 전제.
