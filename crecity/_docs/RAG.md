## 1. 결론

**지금 당장 RAG를 넣을 자리는 없다.** 이 프로젝트는 거래형 마켓플레이스라
"문서 뭉치에서 찾아 답하는" 문제 자체가 적다. 백로그도 AI 브리프(#39)와 Instant Creator
Match(#40)를 명시 보류했고, 둘 다 LLM 없는 대체안으로 이미 해결했다
(#49 브리프 템플릿, #99 필터 기반 추천).

후보는 세 곳이며, 우선순위는 다음과 같다.

| 순위 | 후보 | 성격 | 착수 조건 |
| --- | --- | --- | --- |
| 1 | 크리에이터 의미 검색 (§3.1) | 벡터 검색(생성 없음) | 승인 프로필 수백 명 이상 |
| 2 | AI 브리프 생성 (§3.2, #39) | 정통 RAG | 생성 LLM 비용 정책 확정 |
| 3 | 운영자 분쟁 판정 보조 (§3.3) | 정통 RAG(보조만) | 판정 완료 분쟁 이력 축적 |

## 2. 현재 상태 — 검색·추천이 어떻게 동작하는가

| 기능 | 현재 구현 | 한계 |
| --- | --- | --- |
| 크리에이터 키워드 검색 `q` | `name`·`tagline` ILIKE 부분 일치 | `bio`·패키지 `description`·프로필 FAQ는 검색 대상 아님. 자연어 질의 불가 |
| 유사 크리에이터 (#88) | 같은 카테고리 후보를 도메인 순수 함수 `similarity.rank_similar`로 순위화(플랫폼 겹침 → 최저가 근접 → 최신) | 텍스트 유사성은 보지 않음 |
| 캠페인 적합 크리에이터 (#99) | 공고 타겟(플랫폼·카테고리·지역·예산)을 기존 목록 필터로 변환(백엔드 변경 0) | 공고 `description`과 크리에이터 `bio`의 의미 일치는 보지 않음 |
| 캠페인 브리프 (#49) | `/tools/campaign-brief` 항목 채우기 → 텍스트 실시간 생성(클라이언트, LLM 없음) | 브랜드 맥락(과거 공고·선택 크리에이터)은 반영 안 됨 |
| 분쟁 판정 | 운영자가 사유 텍스트(10~2000자)를 읽고 REFUND·RELEASE·DISMISS 판정 | 과거 유사 판정·계약 조건·채팅 이력을 운영자가 직접 찾아야 함 |

임베딩·벡터·LLM 관련 코드·의존성은 현재 저장소에 **없다**.

## 3. 후보 상세

### 3.1 크리에이터 의미 검색 — 가장 적합 (다만 "RAG"보다 "벡터 검색")

- **문제**: "뷰티 쇼츠를 잘 찍는 20대 여성 크리에이터" 같은 자연어 질의를 지금 구조로는 받을 수 없다.
  ILIKE는 표현이 조금만 달라도 놓친다.
- **방식**: `bio` + 패키지 `description` + 프로필 FAQ를 프로필 단위로 임베딩한다.
  질의도 임베딩해 **기존 필터(카테고리·플랫폼·가격·지역·팔로워)로 후보를 좁힌 뒤** 코사인 유사도로
  재정렬하는 하이브리드로 간다. 필터를 버리고 벡터만 쓰지 않는다(가격·지역 조건은 의미가 아니라 제약).
- **파급**: 같은 임베딩으로 #88(유사 크리에이터)과 #99(캠페인 추천)를 규칙 기반에서 의미 기반으로
  올릴 수 있다. #99는 공고 `description` 임베딩 ↔ 프로필 임베딩 대조.
- **생성 단계 없음**: 검색 결과를 그대로 보여주므로 LLM이 필요 없다. 임베딩 모델만 있으면 된다.
- **왜 지금이 아닌가**: 프로필 수가 시드 데이터 수준이다. 후보가 수십 명일 때는 필터만으로 충분하고
  의미 검색의 체감 효과가 없다.

### 3.2 AI 브리프 생성 (#39) — 정통 RAG

- **문제**: 브랜드가 캠페인을 한 줄로 설명하면 완성된 브리프를 받고 싶다(collabstr §3.2).
- **검색 대상(근거 문서)**: 모두 프로젝트 안에 이미 있다.
  - #49 브리프 템플릿의 항목·작성 규칙(`www/lib/campaign-brief.ts`)
  - 블로그 가이드 3편(단가 책정 · 캠페인 브리프 · 광고 표기)
  - 브랜드 자신의 과거 공고(`campaigns.description`)
  - 선택한 크리에이터의 패키지 `description`·`usage_rights` 문구
- **생성**: 검색된 근거를 넣어 LLM이 브리프 초안을 쓴다. 결과는 #49 빌더의 항목에 채워 넣어
  사용자가 수정하게 한다(생성 결과를 곧바로 공고로 등록하지 않는다).
- **왜 지금이 아닌가**: #49가 "무엇을 적어야 하는지 모른다"는 실제 문제의 대부분을 해결했다.
  생성 LLM 비용을 정당화할 근거가 약하다.

### 3.3 운영자 분쟁 판정 보조 — 보조에 한정

- **문제**: 분쟁 판정에 필요한 맥락(계약 조건·채팅 협상 이력·과거 유사 판정)이 여러 화면에 흩어져 있다.
- **검색 대상**: 분쟁 사유 텍스트, 주문의 계약 조건(패키지·사용권·수정 횟수), 해당 주문의 채팅 메시지,
  판정 완료된 과거 분쟁(사유 + 판정 + 근거).
- **생성**: 운영자에게 "판정 초안 + 참고한 근거 목록"을 제시한다.
  **판정은 반드시 사람이 한다.** 자동 판정·자동 환불은 하지 않는다.
- **왜 지금이 아닌가**: 판정 완료 분쟁이 없다. 과거 사례 검색은 이력이 쌓인 뒤에야 의미가 있다.

## 4. RAG가 필요 없는 곳 (오판 방지)

| 후보 | 왜 아닌가 |
| --- | --- |
| FAQ·이용안내 챗봇 | FAQ, how-it-works, 페르소나, 약관을 다 합쳐도 수백 줄이다. 통째로 프롬프트에 넣으면 되고 검색 단계가 필요 없다. 챗봇 자체의 필요성도 요구사항에 없다 |
| 채팅 자동 응답 | 주문 전 협상 메시징에 자동 생성을 끼우면 당사자 신뢰 문제가 생긴다. 요구사항에 없다 |
| 운영자 주문 검색(#56) | 주문 번호·상태·당사자 검색은 정확 일치가 정답이다. 의미 검색이 오히려 해롭다 |
| 리뷰 요약 | 3축 평점 + 블러 정책으로 충분하다. 리뷰 수가 요약이 필요한 규모가 아니다 |

## 5. 도입 시 제약 — 프로젝트 원칙과의 충돌 지점

1. **"외부 서비스는 무료 범위만" 원칙.**
   - 임베딩: 로컬 모델(sentence-transformers 다국어 모델 등)로 비용 없이 가능하다. CPU 추론이므로
     프로필 저장 시점에 백그라운드로 계산하고, 질의 임베딩만 요청 경로에서 한다.
   - 생성 LLM(§3.2·§3.3): 무료가 아니다. 무료 티어 존재 여부·한도를 착수 시점에 확인하고,
     없으면 §3.2·§3.3은 기각한다.
2. **저장소.** 현재 이미지 `postgres:17-alpine`에는 pgvector가 없다.
   - 프로필 수천 명 이하: 벡터 DB 없이 간다. 임베딩 테이블(`profile_id` FK + 벡터 컬럼, 3NF 유지)을
     메모리에 올려 코사인 계산한다. 가장 단순하다.
   - 그 이상: `pgvector/pgvector:pg17` 이미지로 교체(같은 PG 메이저라 볼륨 호환). 사용자 확인 후.
3. **아키텍처.**
   - 임베딩 생성·검색은 creator 스포크의 **outbound 포트**(예: `ProfileEmbeddingPort`)로 둔다.
     구현체는 `adapter/outbound/gateways/`. 도메인은 벡터를 모른다(도메인 순수성 계약).
   - 생성 LLM 게이트웨이는 그것을 쓰는 스포크(campaign·admin)의 outbound 포트로 둔다.
     스포크끼리 임베딩을 공유해야 하면(#99: campaign이 creator 임베딩 대조) 허브 포트 경유.
   - 임베딩 갱신은 원자성이 필요 없는 부수효과다 — 프로필 저장 트랜잭션에 넣지 말고
     Outbox 이벤트로 뺀다(BOUNDARIES §1).
4. **응답 스키마 기본값 금지 규칙**은 그대로 적용된다. 유사도 점수를 응답에 실을 경우
   "없을 수 있는 값"이므로 `float | None`으로 둔다.
5. **개인정보.** 임베딩 원문에 이메일·전화번호·정산 계좌 등 비공개 필드를 섞지 않는다.
   공개 프로필에 이미 노출된 텍스트(`bio`·패키지 설명·FAQ)만 쓴다. 채팅·분쟁 텍스트(§3.3)는
   외부 LLM에 보낼 경우 사용자 동의 범위를 먼저 확정한다.

## 6. 착수 조건과 순서

1. **§3.1 의미 검색** — 승인 프로필이 수백 명을 넘겨 필터만으로 후보가 수십 명 이상 남을 때.
   로컬 임베딩 + 기존 필터 하이브리드, 벡터 DB 없이 시작. 검증: 자연어 질의 10건에 대해
   ILIKE 결과와 상위 5건을 비교하는 스모크 항목 추가.
2. **§3.2 AI 브리프** — 생성 LLM 비용 정책이 확정된 뒤. #49 빌더에 "초안 채우기" 버튼으로 붙인다.
3. **§3.3 분쟁 보조** — 판정 완료 분쟁이 수십 건 쌓인 뒤 재평가. 보조 한정 원칙 유지.

착수하면 이 문서의 지위를 **결정**으로 바꾸고, 채택한 임베딩 모델·저장 방식·비용 정책을 §5에 기록한다.
